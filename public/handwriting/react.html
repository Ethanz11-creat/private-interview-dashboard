01 · 先明确要实现什么

面试题可以这样描述

这是根据你的手撕需求整理的教学题，不对应一个额外的在线题号。

给定用户问题 question、模型调用函数 llm(messages)、工具注册表 tools 和最大模型调用次数 max_steps，实现一个 ReAct 风格的执行器。

  1. 保存系统规则、用户问题与后续交互历史。
  2. 每轮将完整历史传给模型，模型返回结构化动作。
  3. 若是工具动作，校验工具名与参数结构，执行已注册工具，将真实结果作为 Observation 加入历史。
  4. 若是最终回答，返回答案并停止。
  5. 解析、校验或工具执行失败时，将错误作为 Observation 回传，允许下一轮修正。
  6. 达到最大步数仍没有最终回答时，停止并返回“任务尚未完成”的提示。

输入与输出接口

参数约定
question用户问题，字符串
llm可调用对象；输入消息列表，返回 JSON 字符串；不修改传入历史
tools字典：工具名 → Python 函数；函数有说明用途与参数的 docstring
max_steps正整数，最大模型调用次数，包含生成 final 的那一轮
工具返回值能被 json.dumps 序列化；演示工具返回数值
执行器返回值答案字符串，或预算耗尽后的未完成提示

约定两种模型输出

调用工具

{
  "type": "tool",
  "name": "get_price",
  "args": {"product": "商品A"}
}

结束任务

{
  "type": "final",
  "answer": "商品A买3件，总价为37.5元。"
}

工具结果由程序产生，例如 Observation: {"ok":true,"result":12.5}。模型只提出动作；Observation 不能由它自己伪装成已经执行的结果。

学习目标：这份代码是面试教学用的最小执行器，用标准库即可跑示例。真实模型通过注入的 llm 函数接入；本页没有填写某一家模型 API 的密钥或 SDK 调用。
02 · 先看控制流

ReAct 的关键是结果能影响下一步

ReAct 将模型推理与外部行动交替结合，工具反馈帮助后续决策。原论文常用 Thought、Action、Observation 描述这种交互。本教学实现让模型内部完成决策，运行器只接收结构化工具动作或最终回答，不要求输出完整内部思考过程。

概念来源：ReAct: Synergizing Reasoning and Acting in Language Models（原论文）。下面的 JSON 协议与 Python 运行器是教学设计，并非论文指定的唯一接口。

谁负责什么？

参与者职责本例
模型根据当前问题和历史提出工具动作，或生成最终回答选择查价，再根据价格选择乘法
执行器控制循环、解析协议、校验工具、执行并保存结果react 函数
工具完成具体操作，返回真实结果get_price、multiply
Observation执行器回传给模型的成功结果或错误12.5、37.5 或异常说明
为什么必须再调用模型？查价结果 12.5 只是中间信息，用户还要求计算三件总价。执行器把它加入历史，下一轮模型才能带着 12.5 提出乘法动作。只返回第一次工具结果，没有完成整个问题。

你可以把工具注册表类比为业务 Agent 已加载的工具能力，把 messages 类比为本次任务的工作上下文。这里没有实现持久记忆、Skill 路由或多工具并行，它们可在这个循环周围继续扩展。

03 · 核心函数逐行拆解

手撕时先写循环，再补协议与工具

点击任意代码行查看说明。右侧的例子都围绕“查询商品A单价，再算3件总价”。SYSTEM 与 import 在下方完整代码中。

react · Python 标准库版

完整核心代码：import + SYSTEM + react

import json

SYSTEM = """你是工具型助手。每轮只返回一个 JSON 对象，不输出 Markdown。
调用工具：{"type":"tool","name":"工具名","args":{"参数名":"值"}}
结束回答：{"type":"final","answer":"最终答案"}
只能使用工具清单中的工具，参数名必须与工具说明一致。
Observation 是程序回传的工具结果；根据它决定下一次动作。
出现错误可以修正动作；结果不足时不要编造工具结果。
"""


def react(question, llm, tools, max_steps=5):
    if max_steps < 1:
        raise ValueError("max_steps 必须至少为 1")
    tool_info = "\n".join(f"{name}: {fn.__doc__}" for name, fn in tools.items())
    messages = [
        {"role": "system", "content": SYSTEM + "\n工具清单：\n" + tool_info},
        {"role": "user", "content": question},
    ]
    for _ in range(max_steps):
        raw = llm(messages)
        messages.append({"role": "assistant", "content": raw})
        try:
            action = json.loads(raw)
            if action["type"] == "final":
                if not isinstance(action["answer"], str):
                    raise ValueError("answer 必须是字符串")
                return action["answer"]
            if action["type"] != "tool":
                raise ValueError("type 必须是 tool 或 final")
            name, args = action["name"], action["args"]
            if not isinstance(name, str) or not isinstance(args, dict):
                raise ValueError("name 必须是字符串，args 必须是字典")
            if name not in tools:
                raise ValueError(f"未知工具：{name}")
            result = tools[name](**args)
            observation = {"ok": True, "result": result}
        except Exception as e:
            observation = {"ok": False, "error": f"{type(e).__name__}: {e}"}
        messages.append({
            "role": "user",
            "content": "Observation: " + json.dumps(observation, ensure_ascii=False),
        })
    return "达到最大步数，任务尚未完成。"

复制按钮只复制 react 函数；单独运行还需要上面的 import json 与 SYSTEM。函数中的 for 循环才是最重要的手撕部分，异常与协议检查可以按面试要求说明后补全。

04 · 可以直接跑通的离线示例

两个工具 + 一个模拟模型

把下面代码接在完整核心代码后面，保存为 Python 文件执行即可。演示价格是虚构的本地数据，不需要联网或 API Key。

# 将这段放在上面的核心代码之后，就能直接运行。
def get_price(product):
    """查询演示商品单价；参数 product: str；返回 float。"""
    prices = {"商品A": 12.5, "商品B": 20.0}
    return prices[product]


def multiply(a, b):
    """计算两个数的乘积；参数 a: number, b: number；返回 number。"""
    return a * b


def mock_llm(messages):
    # 固定问题的演示脚本，不是真实大模型。
    observations = [
        json.loads(m["content"].split("Observation: ", 1)[1])
        for m in messages
        if m["role"] == "user" and m["content"].startswith("Observation: ")
    ]
    if not observations:
        action = {"type": "tool", "name": "get_price", "args": {"product": "商品A"}}
    elif not observations[-1]["ok"]:
        action = {"type": "final", "answer": "演示工具出错，无法完成计算。"}
    elif len(observations) == 1:
        price = observations[0]["result"]
        action = {"type": "tool", "name": "multiply", "args": {"a": price, "b": 3}}
    else:
        total = observations[-1]["result"]
        action = {"type": "final", "answer": f"商品A买3件，总价为{total}元。"}
    return json.dumps(action, ensure_ascii=False)


if __name__ == "__main__":
    tools = {"get_price": get_price, "multiply": multiply}
    answer = react("查商品A单价，并计算买3件的总价。", mock_llm, tools)
    print(answer)  # 商品A买3件，总价为37.5元。
模拟模型的范围：mock_llm 是针对固定演示问题写好的三步脚本，利用历史中的 Observation 取得价格和乘法结果。它不是真实大模型，也不能理解任意新问题。实际决策能力来自替换后的真实 llm，而 react 控制循环可以继续复用。

06 · 面试官常追问的实现细节
闭环的几个关键点
1. messages 和 tools 不是一回事
messages 是本次任务的对话状态；tools 是程序允许调用的函数集合。模型在文本里输出工具名，并不会自动调用 Python 函数。
tools = {"multiply": multiply}
name = "multiply"
args = {"a": 12.5, "b": 3}

fn = tools[name]
result = fn(**args)  # 相当于 multiply(a=12.5,b=3)
字典里存 multiply 函数本身，不能注册成 multiply()，后者会在注册时立即调用函数。
2. JSON 解析不是 Python 执行
json.loads(raw) 将字符串解析为对象。它不会执行工具，也不会执行 Python 表达式。解析成功后仍需检查动作类型、工具名与参数，再显式查表执行。不要用 eval 解析模型文本。
3. 为什么错误也要成为 Observation？
错误能为下一轮提供可修正的信息。例如 get_price 的参数名误写为 item，函数签名会抛出 TypeError；模型看到错误后可以改成 product。这里的执行器提供恢复机会，但模型不一定成功修正，因此仍需要最大步数。
本示例检查字段结构与工具存在性；完整参数类型、范围与业务校验应由工具或 schema 校验层承担。Python 函数注解本身也不会自动校验参数类型。
4. 为什么 llm(messages) 没有放进同一个 try？
该 try 针对解析、协议与工具执行。模型服务故障不一定生成有效动作，通常由 llm 适配层处理超时、重试或向调用者报错。最小执行器没有覆盖网络失败，不应说它“捕获了所有异常”。
5. return 工具结果与 return 最终答案不同
工具函数 return 表示这个工具执行结束；react 还要继续循环。只有有效 final 才从 react 返回成功答案。预算耗尽返回的是未完成提示，不能伪装成完成了任务。
6. 这是文本 JSON 协议，不是原生 function calling 消息
本页将动作保存为 assistant 文本，将 Observation 放进 user 文本，是为了讲清楚不绑定 SDK 的控制流。若接入原生工具调用，通常需要记录模型返回的工具调用对象，并使用与之匹配的工具调用标识回传 tool 消息；不能把这里的 role 原样视为所有 SDK 的工具协议。
7. 是否必须打印 Thought？
运行器完成闭环所需的是动作、工具反馈和终止判断。模型可以在内部决策，工程日志记录工具选择与简短决策摘要即可；无需要求它公开完整内部思考过程。原论文的提示格式与本页的工程接口是两个层面的概念。
8. 多个工具可以并行吗？
本最小版每轮只接受一个工具动作，串行执行。若模型一次提出多个彼此独立的工具调用，可以扩展执行器并行执行后汇总结果；有依赖的调用仍要等前一步 Observation。查价后用价格算乘法就是依赖关系，不能在价格未知时同时执行两步。
9. 复杂度怎样说？
设模型调用上限为 K，框架最多执行 K 轮，工具调用最多也是 K 次，通常最后一轮用于 final。但实际时间主要由模型与工具延迟决定，不能将整套 Agent 的时间笼统说成常数操作的 O(K)。
部分分析
循环框架最多 K 次模型调用；每轮最多执行一个工具
历史消息条数O(K)，但消息字节 / token 总量取决于每次输出长度
存储的历史文本初始内容 + 所有动作 + 所有 Observation 的总大小
每轮发送完整历史若每轮新增约 L 个 token，累计输入约 O(K²L)，加上 K 次初始上下文；不是单纯 O(KL)
实际端到端耗时各轮模型延迟 + 工具延迟 + 解析与传输开销之和
这里没有上下文压缩。大结果裁剪、总 token 预算与超时可以作为工程扩展；max_steps 自身只能控制轮数。


07 · 由口述写到代码
记忆顺序：历史 → 决策 → 分支 → 执行 → 反馈 → 再决策
① 搭循环
建 messages，for 限制次数，每轮 llm(messages)。
② 分动作
解析 JSON，final 返回；tool 检查工具名与参数。
③ 执行工具
tools[name](**args)，成功或异常都生成 Observation。
④ 维持闭环
动作与 Observation 都保存进历史，再进入下一轮。

约 1 分钟面试口述
“我把 ReAct 写成一个带状态的循环。先保存系统规则、用户问题和工具清单，每轮把完整历史交给模型，让它返回一个结构化动作。
如果是 final，我直接返回答案。如果是工具动作，我先检查类型、工具名和参数结构，再从注册表取函数执行。工具成功时记录结果，解析或执行失败时记录错误，都作为 Observation 加入历史。
下一轮模型根据新的 Observation 决定继续调用工具还是结束，所以工具结果能够真正影响下一步。为了防止无限循环，我限制模型调用次数；预算耗尽时明确返回未完成。
工具注册、协议解析和执行是运行器的职责，下一步工具选择是模型的职责。这里演示用模拟模型，接真实模型只替换 llm 适配层；如果使用原生 tool calling，需要适配对应的工具消息与调用标识。”
面试追问：ReAct 和固定 Workflow 怎么区分？
固定 Workflow 的任务步骤由程序预先安排。ReAct 的下一次动作由模型结合当前 Observation 动态决定。本页 mock_llm 是固定脚本，所以它只验证运行器，不证明模型具备动态规划能力；接上真实决策模型后，这个循环才承载其动态行为。
如果要结合你的 Agent 项目来讲
可以先展示这个串行最小循环，再说明如何扩展工具路由、并行独立调用、依赖顺序与结果聚合。讲清楚哪些是模型决策，哪些是确定性的执行规则，会比把所有组件都称为 ReAct 更准确。
最该记住的一句：工具执行后，把 Observation 加入历史，再让模型决策。少了这个反馈步骤，代码就没有形成 ReAct 的交互闭环。
